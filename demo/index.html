Interactive companion to the paper

Contrastive Learning for Results-Aware SPARQL Embeddings

Two SPARQL queries can look almost the same and return different answers, or look different and return the same answers. We teach query encoders to place queries by what they return, not by how they are written, using answers collected once, offline. At query time the encoder needs only the query text.

1 What we did

Execute a query log once, label query pairs by the Jaccard overlap of their answer sets, and fine-tune any pretrained encoder with a contrastive loss on these labels. We release the labels as SQuARE (DBpedia + Wikidata).

2 Why it matters

Query retrieval and approximate result caching need answer overlap, but text, code and SPARQL encoders are trained on how queries look. Fine-tuning improves retrieval for all 10 encoders on both graphs.

3 What is new

To our knowledge, the first SPARQL query embeddings trained on execution-derived answer overlap, and the first SPARQL resource with query-pair supervision grounded in execution.

2 How it works

Answers need no human annotation: an endpoint computes them. We collect this evidence once, offline, and the encoder uses only the query text afterwards.

  1. Execute oncecache each query's answers
  2. Label by overlapJaccard J of answer sets
  3. Split without leakageby positive components
  4. Fine-tuneInfoNCE + hard negatives
  5. Use onlinequery text only

  • Every label stays checkable: SQuARE ships the cached answer sets, so J can be recomputed without any endpoint.

Step 3 · Split by connected components of positive pairs

If an anchor is in the test split while its positive is in training, the pair is seen in training and scored again at test time. We avoid this by keeping each connected component of positive pairs in one split.

Step 4 · Contrastive fine-tuning on answer-overlap labels

epoch 0 / 20

Colour = queries with the same answers. They start where text puts them: queries that differ in one constant or predicate sit together.

Each step applies the InfoNCE loss of the paper: pull an anchor toward one of its positives, push it away from its negatives and the other in-batch candidates (known positives are masked). From epoch 2, every two epochs, the current model's closest labeled negatives are mined (red links); they are execution-verified, so they can never be false negatives.

Toy demo: 12 free 2-D points trained live in your browser (distance-based similarity, so you can watch it). Real training updates all weights of a pretrained encoder, with cosine similarity and κ = 0.05.

4 Downstream task 2 · Approximate result caching

  
For each incoming query, reuse the cached answers of its most similar cached query if cosine ≥ θ; otherwise execute it and add it to a FIFO cache (K = 128). A reuse is correct if J ≥ 0.8. Answers are used only to judge decisions, never to make them.

Finding: ranking and calibration are different problems

    
Results-aware fine-tuning makes reuse decisions much better (DBpedia hit accuracy 0.15–0.33 → 0.59–0.79). Still, a single cosine threshold does not make reuse safe: on Wikidata, most hits remain wrong for most encoders at any θ. SQuARE makes this gap measurable, and points to calibrated or verified reuse as the next step.

  







  
5 What is new

  
Prior work is results-blind (learns from how queries are written) or works with relations that are exact but costly. Ours learns graph-specific answer overlap and needs only text at inference.
